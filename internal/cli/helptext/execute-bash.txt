execute-bash — run bash through command approval choreography

Usage:
  tmux-a2a-postman execute-bash --label <label> --command <bash>
  tmux-a2a-postman execute-bash --label <label> --mode blocking --reviewer <node> --command <bash>
  tmux-a2a-postman execute-bash --thread-id <thread> --record-decision approved

Execution flags:
  --label <label>              Command label used for policy matching and audit
  --category <category>        Optional category used for policy matching
  --requester <node>           Requesting node; defaults to current pane title
  --reviewer <node>            Reviewer override
  --mode <mode>                advisory, warn-only, or blocking
  --reason <text>              Reason stored on approval requests and decisions
  --command <bash>             Bash string run with bash -lc
  --approval-ttl-seconds <n>   Approval request expiry; default is 900
  --override-approval          Continue in warn-only mode without approval
  --store-command-text         Store full command text in audit events
  --json                       Emit wrapper metadata as JSON on stderr
  --no-wait                    In blocking mode, return the current pending/
                                blocked result immediately instead of waiting
                                for the approval thread to resolve
  --wait-timeout-seconds <n>   How long blocking mode waits for a decision
                                before giving up; default is 300 (5 minutes)

Decision flags:
  --thread-id <thread>         Approval thread id to decide or reuse
  --record-decision <decision> approved or rejected. The decision's reviewer
                                identity is always the calling process's own
                                tmux pane title, never --reviewer; a caller
                                whose pane is not the thread's command_approver_node
                                is refused and no decision is recorded.

Modes:
  advisory   Records request and audit metadata, then runs even without approval.
  warn-only  Records request and blocks unless --override-approval is supplied.
  blocking   With a trusted, resolvable reviewer, waits (bounded by
             --wait-timeout-seconds, default 300s) for the matching thread's
             decision and then runs the command in the same invocation --
             pass --no-wait to return the current pending/blocked result
             immediately instead of waiting (status/exit-code contract is
             the same either way; --no-wait only skips the polling).
             Runs only when the resolved decision is a non-expired approved
             decision from the configured reviewer for the exact command
             digest, AND only once: an approval is single-use, so a
             concurrent or repeated call after execution gets
             "already_executed" instead of running again -- until that
             approval's own TTL expires, at which point a retry mints a
             fresh request automatically. Rejection, expiry, a wait
             timeout, cancellation (SIGINT/SIGTERM, including precisely
             during the approval claim), a requester mismatch, delivery
             failure, mid-wait approver loss, a context/session-generation
             change, and no live current session writer (session_unavailable,
             a genuine cold start with no bootstrapped session yet) each
             produce a distinct --json "status" and process exit code
             (10-23). These exit codes can numerically collide with the
             executed command's own exit status (0-255) -- the --json
             "status" field is the authoritative way to tell them apart,
             not the bare exit code. Retrying the identical command always
             converges instead of sticking forever: no request yet creates
             one; a still-pending request is reused and re-delivered
             (recovering a failed delivery without duplicating the
             request); a rejected, expired, stale, historical-only, or
             wrong-reviewer thread is superseded by a freshly minted
             request on the next call. A requester mismatch, digest
             mismatch, or unresolvable approver is a refusal and never
             mints -- including when a concurrent racer for the same
             thread wins with a different policy context: the loser
             refuses and never delivers a prompt describing its own,
             different policy under the winner's correlation. See
             docs/command-approvals.md.

Fail-open rule (command_approver_node):
  When no command_approver_node is configured by marking a real node in
  postman.md Mermaid edges with class <node> command_approver_node (same
  family as ui_node), every mode above, including blocking, fails open. Every
  command runs and is recorded distinctly as auto_approved_no_reviewer rather
  than a real approval. The approver is global; per-policy approver routing is
  not supported. A configured but currently unresolvable
  command_approver_node is different: blocking fails closed and does not run
  the command; advisory continues; and warn-only still requires explicit
  --override-approval. An unresolvable command_approver_node also produces a
  load-time warning and a visible marker in get-status.

  When a valid command_approver_node exists, execute-bash also delivers the approval
  request to it directly as a reply-required message; reply with a body
  starting APPROVED:/NOT APPROVED: while preserving the given thread_id, the
  exact fills_input_request_id, and command_hash frontmatter fields to record
  a decision without running --record-decision yourself. A reply body that
  doesn't start with one of those two prefixes is logged and not recorded.
  Only a reply whose sender matches the resolved command_approver_node is ever
  honored, regardless of the reviewer audit label. The same rule applies to
  --record-decision itself: the decision's reviewer identity is always the
  calling process's own tmux pane title, never the --reviewer flag, and a
  caller whose pane is not the command_approver_node is refused outright.

Bypass boundary:
  This wrapper coordinates command review through Postman. It does not sandbox
  bash, prevent direct shell execution, or enforce OS-level policy. Use it for
  local agent choreography and durable audit trails, not as a security boundary.

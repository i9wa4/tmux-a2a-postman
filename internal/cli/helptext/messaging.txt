Messaging — send and receive messages

The send-heredoc, pop, and get-status workflow below uses the file-first
workspace path. Legacy daemon inspection and status fields are identified
separately below.

Quick workflow (agents):
  Send:
    tmux-a2a-postman send-heredoc --to <node> <<'POSTMAN_BODY'
    message text
    POSTMAN_BODY
  Claim/open: tmux-a2a-postman pop

Safe body input:
  Use send-heredoc with a quoted heredoc delimiter for frequent agent-to-agent
  messages. The quoted delimiter preserves command substitutions, backticks,
  $HOME variables, quotes, code fences, and shell examples as literal text.
  Do not pass message text through argv, file-body shortcuts, or generic
  pipe-oriented guidance.

Reply workflow:
  Reply-required messages carry an input_request_id. Exact replies use:
  tmux-a2a-postman send-heredoc --to <sender> --fills-input-request-id <input_request_id> --reply-to <message_id> <<'POSTMAN_BODY'
  DONE: ...
  POSTMAN_BODY

The --fills-input-request-id and --reply-to values must identify the same
claimed request; together they close that exact required action. Replies use
the same file-first send path as other messages.
After a reply, check the returned file-derived `self` state for the exact
inbound obligation and any remaining required replies. Missing or ambiguous
state is unknown, not proof that the obligation closed.

Completion gate:
  Filling an input request closes transport, not task acceptance.
  Before DONE, compare the original requirements/checklist against evidence.
  Use this compact proof shape when work is complete:
    DONE: Requirements satisfied.
    Task artifact: <artifact-reference>
    Original checklist: PASS
    Evidence: <commands, issue/PR links, tests, or verification output>
    Remaining blockers: none
  Use BLOCKED with Original checklist: FAIL when any requested item is
  unresolved or unverified. Receivers should verify checklist status, durable
  references, evidence, and blockers before relaying, approving, or closing
  work.

For the retained daemon path, inspect open reply-required work without popping
inbox mail:
  tmux-a2a-postman inspect-input --id <message_id-or-input_request_id>

Legacy daemon get-status also exposes open input-request detail arrays under
nodes[*].flow.input_requests.input_required and waiting_on_input.
When known, those details include opened_event_id and read_event_id pointers
to the journal events that created the visible state.

File-first mail envelope (schematic JSON header in one HTML comment):
  <!-- postman {"id":"<message-id>","from":"<sender>","to":"<recipient>","needs_reply":false,"created_at":"<timestamp>"} -->

A blank line separates that canonical JSON header from the Markdown body.
Reply-required mail also has input_request_id; exact answers have reply_to and
fills_input_request_id. This envelope is not YAML frontmatter.

Retained daemon mail envelope (YAML frontmatter):
  ---
  params:
    from: <sender node name>
    to: <recipient node name>
    messageId: <message filename>
    replyPolicy: <none|required>
    input_request_id: <required reply token>
    timestamp: <ISO 8601 timestamp>
  ---

Sender is auto-detected from the tmux pane title (no --from flag).
`send-heredoc` and `pop` print JSON by default. File-first `pop` moves the
next eligible own inbox message to its read archive before returning metadata
and an archived body path; it does not print the full body inline.

After every successful `pop` with `status=message`, read the complete archived
Markdown body before any handling, routing, reply, status decision, or
no-action or no-op decision.
`messageType: ping`, `replyPolicy: none`, and other JSON metadata do not allow
skipping the archived body. Truncated command output from `cat`, `sed`, `rg`,
shell logs, or other bounded stdout paths is not a complete read; use a
complete file-read path or verified chunks through EOF.
